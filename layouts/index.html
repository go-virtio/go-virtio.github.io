Why go-virtio

Every Go project that talks to a virtio device today re-implements the same plumbing : walk the PCI capability chain, pin the modern-config registers, build a split-virtqueue, drive the per-device-class state machine. The code is largely identical from project to project, but it's pasted into each codebase and tested only against the one transport that project happens to use. go-virtio factors the shared pieces out into common, expresses the host-side dependency as a small Transport interface, and ships per-device-class drivers (net, blk, …) on top — reusable, well-tested, and portable across backplanes.

The stack

Spec-level drivers

One Go module per virtio device-class. Each owns the per-frame layout, feature-acceptance mask, init sequence, and per-queue state machine for that class.

go-virtio/common

The single waist. PCI cap walker, modern-config layout (Virtio 1.1 §4.1.5), split-virtqueue, and the Transport interface every driver consumes.

Host backplane

Anything that satisfies Transport: UEFI's EFI_PCI_IO_PROTOCOL, bare-metal MMIO, virtio-mmio adapter, in-process test harness. Drivers don't know the difference.

Repositories

common

Transport-agnostic infrastructure: PCI capability walker, ModernConfig handle, split-virtqueue, transport interfaces. Coverage at ~96%, climbing to 100%.

net

Pure-Go virtio-net driver. Modern-transport init sequence, split-ring TX/RX path for the standard PCI virtio-net device (VID 0x1AF4, DID 0x1041). 100% coverage target.

blk

Pure-Go virtio-blk driver. Placeholder today; activates when a concrete caller (microVM block device during pre-EBS) needs the request-virtqueue path.

Quality bar

  • Pure Go. CGO_ENABLED=0 across the org. No host driver shim, no kernel dependency.
  • 100% test coverage. Every module is gated on it. Error branches, not just happy paths.
  • Spec-traceable. Every register, descriptor field, and feature bit cites the Virtio 1.1 section it implements.
  • Transport-pluggable. The same driver code drives a real device under UEFI, a virtio-mmio adapter on bare metal, and an in-process harness in tests.
  • Multi-arch. No architecture-specific assembly. Same source on amd64, arm64, riscv64, loongarch64.
  • BSD-3-Clause on every source file.

Who uses it

The first consumer is cloud-boot — specifically the pure-UEFI TamaGo loader that drives the guest's virtio-net NIC during PXE / HTTP boot under Apple Virtualization.framework and KVM/OVMF. The intent is that any Go project running close to the metal — microVM runtimes, bootloaders, unikernels, test harnesses — can pull in go-virtio/* instead of re-implementing the same struct virtio_pci_cap walk.
